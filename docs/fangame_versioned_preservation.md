# Fangame Versioned Preservation / Time Machine v0.1

## Goal
Preserve every meaningful release (original, fixed, patch, repack) as a verifiable state without blindly duplicating the whole game for every version.

The preservation unit is a **release state**, not merely a download page and not merely a copied archive.

Each release must answer:

- What exact release/version is this?
- Where did it come from and how was it acquired?
- Is the original package byte-verified?
- What files/content does this release contain?
- What changed from its parent release?
- Can we reconstruct/rollback to this release?
- If not, exactly what evidence/object is missing?

## Two fidelity lanes

### A. RAW / archive fidelity
For the downloaded package itself.

Record at minimum:

- package byte size
- SHA-256
- MIME / file header
- original filename if known
- source URL/share ID/source lineage
- acquisition transport
- archive/SFX type

Do **not** keep a full duplicate of every raw package by default.

Storage policy:

1. Keep a full raw package as a **checkpoint** for the first preserved release and for major/repacked releases.
2. For a later minor/fix release, attempt a binary delta against the nearest checkpoint/parent (`xdelta3` or equivalent).
3. Keep the delta only when it is materially smaller than a full package.
4. If delta size is >= 60% of the full raw package, or the package was completely repacked/recompressed, store a new full checkpoint instead.
5. Maximum delta-chain depth: 4. After that create a fresh checkpoint.

A release is `BYTE_EXACT_RECONSTRUCTABLE` only when rebuilding the raw package produces the recorded package SHA-256.

### B. CONTENT / extracted-tree fidelity
For what is actually inside the game.

Every release gets a deterministic file manifest:

- relative path
- byte size
- SHA-256
- release root hash
- total files / total bytes

Between parent and child release, generate a semantic file diff:

- added
- removed
- changed
- unchanged
- renamed/reused-by-hash candidates
- reused bytes
- new/changed bytes

For content storage, unchanged files are never copied merely because a new release exists. A fix release stores only newly introduced/changed objects plus its manifest/deletion list.

A release may therefore be `CONTENT_EXACT_RECONSTRUCTABLE` even when its original compressed archive cannot be regenerated byte-for-byte.

## Why both lanes are required
Two ZIP/EXE/RAR packages can contain the same game files but have different compression metadata, timestamps, ordering, or installer wrappers. A file-tree manifest proves content identity; the raw package SHA proves original-package identity. Do not conflate them.

## Release kinds

- `ORIGINAL` — earliest/base release
- `FIX` — bug-fix/revised release
- `PATCH` — patch-only distribution
- `REPACK` — same/similar content repackaged
- `MAJOR` — materially new release
- `UNKNOWN` — relation not yet proven

Each release has `parent_release_id` when the lineage is known.

## Required release record

Each release record should contain:

- `game_id`
- `title`
- `release_id`
- `version`
- `release_kind`
- `parent_release_id`
- publication/source evidence
- acquisition log: how it was rescued
- failure log when acquisition failed
- raw package metadata + SHA when available
- content manifest root hash
- parent diff summary
- rollback status
- Drive object/checkpoint/delta references
- verification state

## Verification states

- `IDENTITY_VERIFIED` — release identity/source/version are sufficiently locked
- `RAW_VERIFIED` — downloaded package bytes + SHA verified
- `CONTENT_MANIFEST_VERIFIED` — extracted tree manifest generated
- `CONTENT_EXACT_RECONSTRUCTABLE` — target file tree can be rebuilt and root hash matches
- `BYTE_EXACT_RECONSTRUCTABLE` — original package can be rebuilt and package SHA matches
- `CHECKSUM_PENDING` — package is archived but local/remote byte verification is incomplete
- `BINARY_MISSING` — identity exists but no acceptable package was acquired

`RESCUED` should mean the preservation contract for that target has been satisfied at the required fidelity level; do not silently upgrade content-only recovery to byte-exact recovery.

## Rollback model

Rollback is manifest-driven, not "copy an old folder over the new one".

To restore release R:

1. Read R's manifest.
2. Find the nearest full checkpoint or current object inventory.
3. Reuse objects whose SHA-256 already exists.
4. Fetch/apply only missing/changed objects or delta packs.
5. Remove paths absent from R.
6. Recompute every file hash and the deterministic root hash.
7. If raw reconstruction is required, rebuild/apply raw delta and verify the original package SHA-256.

A rollback is successful only when the requested fidelity hash matches.

## Storage tiers

### Tier 1 — tiny metadata, always keep
Manifest JSON, diff JSON, acquisition/failure log, checksums, lineage, source IDs.

### Tier 2 — changed content only
Changed/new files or content-addressed objects required to reconstruct a release.

### Tier 3 — raw checkpoint
Full downloaded package only for anchor/major releases or when delta efficiency is poor.

### Tier 4 — raw delta
Binary patch from parent/checkpoint when substantially smaller than a new full checkpoint.

## Checkpoint policy
Create a fresh full checkpoint when any is true:

- first preserved release
- major release
- unknown lineage
- repack/recompression makes raw delta >= 60% of full package
- delta chain depth > 4
- parent is not byte-verified
- reconstruction test fails

## RPG Maker-specific semantic diff
When extraction/parsing is available, summarize changed areas separately:

- executable / DLL / RGSS runtime
- `Game.ini`
- encrypted data archive (`Game.rgssad`, `Game.rgss2a`, `Game.rgss3a`)
- `Data/` maps/database/scripts
- `Graphics/`
- `Audio/`
- fonts/plugins/scripts
- saves/config bundled by mistake

For RGSS encrypted archives, keep both the raw archive hash and, when safely extractable, a manifest of its internal tree. This prevents one giant changed `.rgss*` blob from hiding a small real fix.

## Anti-duplication rule
Never create a new Drive full-package copy merely because a new Notion release record exists. First compare hashes/manifests and choose: reuse existing object, delta, or checkpoint.

## First implementation
`tools/fangame_release_manifest.py` provides deterministic release manifests, release-to-release diffs, and rollback object plans. It deliberately does not claim byte-exact raw-package reconstruction by itself; raw delta/checkpoint support is the next layer.
